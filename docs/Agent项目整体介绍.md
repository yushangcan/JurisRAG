# JurisRAG 轻量法律检索 Agent

本版聚焦政府采购与招投标：用户提出问题后，系统识别所问制度、业务场景和争点，查找官方来源的本地快照，逐项检查证据，再给出原文依据或受约束的归纳。代码继续使用已有 Python 技术栈，避免为换语言重写已经可用的解析与法律元数据链路。

## 从一个问题理解系统

用户问“供应商资格条件与证明材料分别是什么”。Agent 识别两个争点，分别检索政府采购法第二十二条和实施条例第十七条。只有两个争点的实际正文都进入最终上下文，系统才形成正式引用。top_k=1 无法放入两条父证据时会停止回答，不能只展示一条却宣称完整。

用户问“投标文件超过150页可以否决吗”。系统把设置文件要求与否决依据分开，并在法律制度不明确时区分政府采购和工程招标。它可以展示库内的一般规则，同时询问项目制度、文件完整要求、评标依据等事实；不直接判断该项目合法或违法。

用户问“第九十九条是什么”。明确法规但条号不存在时拒答；只有条号时追问法规名。上一轮是明确法规原文查询，下一轮说“那第十三条呢”，系统承接法规名称并替换条号，不把旧条号也当成本轮要求。

## 为什么这样设计

此前项目的复杂度主要来自强制向量依赖、Chroma、LangGraph、跨进程 MCP、多次模型规划与审查。当前任务并不需要多服务协作或任意工具调用。改为单进程有限循环后，主服务保留 4 项直接依赖，可离线完成检索、证据检查和原文回答。

SQLite 存父法条、子切片、来源元数据和 FTS5 索引。中文使用二元字串，无需下载分词模型。已有官方快照共 80 份记录，去重后 66 份文档、1,565 个父块、2,299 个子块。向量与重排是按需开启的增强能力，MCP 是外部适配器。

## Agent 超出基础 RAG 的部分

基础 RAG 只做一轮同库检索。Agent 多了场景争点规划、法源定位、多查询、缺口观察、有限补查、最终证据覆盖复核及追问。23 个场景规则保存的是待查问题和法源位置，法律结论从本次实际检索的原文产生。

默认最多 2 轮检索和 2 次模型调用。模型仅在需要补检改写或归纳时使用；明确法条查询零调用。重复查询、没有新证据、正式引用缺失、超时或预算用完都会终止。预算耗尽不会把证据不足改成可回答。

可选模型的输出包含逐条陈述、证据 ID、原文引文。无效 ID、伪造引文、无依据数字与部分明显越界结论会触发原文回退。这些检查有明确覆盖范围，不能宣称解决全部幻觉问题。

## 工程交付边界

- 原文哈希、冻结 Markdown 摘要、父子关联和官方来源构成可追溯链。
- 入库使用临时文件与原子替换，失败保留旧库。
- HTTP 同时提供页面、问答、健康检查、场景目录与证据全文。
- 请求长度、历史长度、并发、单次模型等待与总等待有界。
- 日志只保留请求 ID、状态、耗时和异常类型，不记录问题或密钥。
- 评测保留题集、实现与索引哈希，失败样本不隐藏。

启动与实际回归报告见 [README](../README.md)。开发集召回率不代表法律回答准确率；本轮没有进行法律专家盲评或付费模型质量评估。法规效力、地方年度政策和具体项目适用仍需官方核验。
