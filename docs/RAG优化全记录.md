# JurisRAG 全部优化记录

> 本文按“原本是什么、存在什么问题、修改了什么、结果如何、证据边界是什么”记录项目演进。数值只引用已有评测报告，同一行的前后对比必须使用同一数据集。

## 一、初始基线

最初版本的目标是先建立最小闭环：读取法规原文，固定字符切块，生成向量，保存到 Chroma，根据问题返回 Top-K，并通过 FastAPI 输出回答和来源。

| 项目 | 初始实现 |
| --- | --- |
| 语料 | manifest 登记的 10 份法规 |
| 输入格式 | DOCX、HTML、PDF 基础读取 |
| 切块 | 全文空白归一化后，每 500 字切一块，重叠 80 字 |
| Embedding | 128 维字符 SHA-256 哈希向量 |
| 数据库 | 单个 Chroma collection |
| 检索 | 单路向量 Top-K |
| 回答 | 可选 DeepSeek；未配置时返回原文证据 |
| 评测 | 最初没有固定 gold 数据集和拒答测试 |

10题 `legal_rag_gold_v1` 的首次可复现结果：Recall@1=0.20、Recall@3=0.30、Recall@5=0.50、MRR@5=0.2900，平均检索延迟14.55 ms。这说明基线速度快，但语义能力、法条结构和排序质量不足。

## 二、可比实验总表

### 1. 10题 v1：分块和混合检索演进

| 阶段 | 主要变化 | Recall@1 | Recall@3 | Recall@5 | MRR@5 | 平均延迟 |
| --- | --- | ---: | ---: | ---: | ---: | ---: |
| 固定字符 + 哈希向量 | 初始评测基线 | 0.20 | 0.30 | 0.50 | 0.2900 | 14.55 ms |
| 结构化 Markdown 切块 | 按章节/法条切块，仍为哈希向量 | 0.20 | 0.40 | 0.50 | 0.3033 | 19.88 ms |
| 父子切块 + 混合检索 | 精确匹配、BM25、向量、RRF、parent 回填 | 0.30 | 0.70 | 0.80 | 0.5083 | 130.99 ms |
| 扩充到66份唯一文档 | 保持父子混合检索，增加更多干扰文档 | 0.30 | 0.60 | 0.80 | 0.4833 | 562.68 ms |

结论：单独改变结构化切块只带来有限排序改善；父子切块与混合检索组合把同一10题集的 Recall@5 从0.50提高到0.80。语料扩展到66份后 Recall@5 仍保持0.80，但 Recall@3、MRR和延迟受到更多候选影响。

### 2. 50题 v2：Embedding 与 Reranker 消融

| Embedding | Reranker | Recall@1 | Recall@3 | Recall@5 | MRR@5 | 平均延迟 |
| --- | --- | ---: | ---: | ---: | ---: | ---: |
| 128维字符哈希 | 无 | 0.45 | 0.70 | 0.84 | 0.6107 | 158.85 ms |
| BGE-small-zh-v1.5 | 无 | 0.57 | 0.84 | 0.90 | 0.7140 | 361.80 ms |
| 128维字符哈希 | BGE Reranker | 0.62 | 0.86 | 0.90 | 0.7457 | 5458.59 ms |
| BGE-small-zh-v1.5 | BGE Reranker | 0.62 | 0.85 | 0.95 | 0.7530 | 5969.48 ms |

结论：在不使用 Reranker 时，中文 BGE 将 Recall@1 提高12个百分点、Recall@5提高6个百分点、MRR@5提高0.1033；在 BGE 基础上加入 Reranker 后，Recall@1和Recall@5分别再提高5个百分点，MRR@5提高0.0390。代价是平均检索延迟从361.80 ms上升到5969.48 ms。

### 3. 证据门和拒答

| 数据集 | 结果 |
| --- | --- |
| 50题有答案集 | 放行50/50，错误拒答0，Recall@5保持0.95 |
| 10题无答案集 | 正确拒答10/10，不安全回答0 |
| 50题有答案集二次召回触发率 | 0% |

结论：证据门在当前有答案开发集上没有造成误拒答，并在10道无答案开发题上完成拒答。但多路召回没有在50道有答案题上触发，因此当前数据不能证明 HyDE 提升了 Recall。

## 三、逐项优化记录

## 优化 1：离线入库与在线检索分层

**原本是什么**

最小基线已经能建库和查询，但模块职责较少，继续增加解析、审计、检索和安全逻辑后容易互相耦合。

**存在的问题**

- 文档处理失败可能直接影响在线查询代码。
- 配置、数据模型和数据库连接容易重复定义。
- 难以单独测试“数据是否正确”和“检索是否正确”。

**修改措施**

- `offline_ingestion/` 负责原文读取、Markdown 转换、审计、切块和建库。
- `online_retrieval/` 负责查询改写、召回、融合、重排、证据门和回答。
- `shared/` 统一管理配置、数据结构、Embedding、Reranker 和 Chroma。
- `evaluation/` 独立保存数据集和评测脚本。

**结果**

离线数据处理和在线 API 可以独立运行；当前项目自动化测试为38项通过。该项属于架构可维护性优化，没有单独的 Recall 消融结果。

## 优化 2：扩大并去重法律语料

**原本是什么**

初始 manifest 只有10份法规，覆盖范围有限。

**存在的问题**

许多政府采购方式、评审专家、进口产品、中小企业、代理机构、投诉和工程招投标问题没有对应文件，检索算法再好也无法回答知识库外问题。

**修改措施**

- 增加政府采购核心法规、部门规章、规范性文件和工程招投标衔接文件。
- 主清单保存20份逻辑文档；外部法律汇集保留60份原始文档。
- 合并时同时按稳定 `document_id` 和原文件 SHA-256 去重；同 ID 但标题或哈希不同则拒绝入库。

**结果**

最终接受66份唯一文档，跳过14份重复文档，生成1,565个 parent 和2,299个 child。10题 v1 在扩充语料后 Recall@5保持0.80，但平均延迟从130.99 ms升至562.68 ms，说明覆盖扩张同时带来候选规模成本。

**证据边界**

“66份”是去重后的入库文档数，不等于全国政府采购法律体系已经完整，也不表示文件当前仍然有效。

## 优化 3：原文件完整性与来源审计

**原本是什么**

基线读取 manifest 中的文件，但缺少覆盖整个转换链路的强制质量门。

**存在的问题**

文件被替换、下载不完整、Markdown 被手工修改或元数据指向错误文件时，仍可能进入索引，造成不可追溯的错误引用。

**修改措施**

- 保存来源平台、来源 URL、附件 URL、文号、日期和 SHA-256。
- 建库前重新计算原文件哈希。
- 外部汇集要求 `SHA256SUMS.txt`、补充清单、Markdown front matter、转换审计报告四方一致。
- 同时校验派生 Markdown 自身的 SHA-256，发现修改立即停止建库。

**结果**

当前60份法律汇集全部完成 Markdown 转换，审计警告为0；语料加载验证得到66份唯一文档、14份重复跳过。该项保证数据完整性，没有独立 Recall 增益。

## 优化 4：DOCX、HTML、PDF 统一抽取

**原本是什么**

输入格式不同，各自包含段落、网页标签、表格或分页信息。

**存在的问题**

- HTML 导航、脚本和样式会污染正文。
- DOCX 段落结构和 PDF 页面结构不同。
- 直接拼接文本会丢失章节层级、表格和页码。

**修改措施**

- DOCX 使用 `python-docx` 按段落读取。
- HTML 使用 BeautifulSoup 清理页面并提取正文块。
- PDF 结合 pypdf/pdfplumber 提取页级文本和表格。
- 统一输出 `ExtractedSource` 和带页码的 `SourceBlock`，让后续结构解析不依赖输入格式。

**结果**

三类格式可以进入同一 Markdown 转换和切块流程；PDF 文档能够继续携带真实页码。属于输入兼容性优化，没有单独的检索指标。

## 优化 5：结构化 Markdown 中间层

**原本是什么**

基线直接把原文读取为纯文本后切块。

**存在的问题**

纯文本难以稳定区分法规标题、章节、法条、普通通知标题和前言；每次建库都要重新猜测结构。

**修改措施**

- 将法规标题转为 `#`，章节转为 `##`，法条转为 `###`。
- 对没有“第X条”的通知、意见、目录和附件建立普通标题层级，不伪造法条。
- 用 YAML front matter 保存原文件、来源、文号、日期和哈希。
- PDF 页面变化处写入 `<!-- page: N -->`。
- 转换完成后生成审计报告，统计文档、法条、页码和警告。

**结果**

外部汇集60份文档全部转换，其中21份按法条解析、39份按普通章节解析，共识别916条法条，7份PDF保留页码，警告0。10题结构化切块阶段 Recall@3从0.30升至0.40，Recall@5仍为0.50，说明结构中间层主要先解决可解释性，不能单独替代检索优化。

## 优化 6：从全局固定字符切块到结构感知父子切块

**原本是什么**

全文压成一行后按500字符切分，相邻块重叠80字符。

**存在的问题**

- 法条可能在任意字符处被截断。
- 检索片段过短时无法支持完整法律语义。
- 直接扩大 chunk 又会降低精细检索能力。

**修改措施**

- 先把完整法条或普通章节作为 parent。
- 对过长 parent 按逻辑段落切为最多500字符的 child，相邻 child 重叠80字符。
- child 负责向量和词法检索，parent 只负责通过 ID 回填完整上下文。
- parent 和 child 分别保存在两个 Chroma collection 中。

**结果**

最终形成1,565个 parent 和2,299个 child。与混合检索共同启用后，10题 v1 的 Recall@5从0.50升到0.80，MRR@5从0.3033升到0.5083。

**证据边界**

这次版本同时引入父子块、精确匹配、BM25和RRF，因此不能把全部数值增益只归因于父子切块。

## 优化 7：页码精确切分和引用

**原本是什么**

早期 chunk 只有文件名和 chunk 序号，没有可靠页码；跨页 chunk 也可能只标一个页码。

**存在的问题**

用户无法根据引用回到 PDF 的确切页面，跨页内容可能被错误标注为单页证据。

**修改措施**

- PDF 转 Markdown 时插入真实页面标记。
- child 切块优先限制在同一页内。
- parent 保存 `page_start`、`page_end`、`page_numbers`；仅单页节点设置唯一 `page_number`。
- DOCX/HTML 没有稳定原始页码时保持为空，不伪造页码。

**结果**

API 引用可以返回准确单页或页码范围；审计会检查 PDF 提取页与 Markdown 页面标记是否一致。该项是溯源正确性优化，没有单独 Recall 指标。

## 优化 8：完整 chunk 元数据

**原本是什么**

基线主要保存标题、来源和 chunk 序号。

**存在的问题**

相似法规和相同条号很多，仅返回“第二十二条”无法说明来自哪部法规，也无法证明文本未被替换。

**修改措施**

每个 parent/child 保存：`document_id`、标题、类别、文号、原文件、Markdown 文件、来源平台、URL、附件 URL、发布日期、施行日期、法律状态、SHA-256、章节、条号、结构类型、标题路径、页码、parent ID、child ID和 child 序号。

**结果**

每条响应可同时展示命中的 child、用于回答的 parent 和官方来源信息，满足面试中“检索结果如何溯源”的问题。该项没有独立 Recall 指标。

## 优化 9：法律编号和专有名词精确匹配

**原本是什么**

所有问题统一进入向量相似度查询。

**存在的问题**

“第22条”“第二十二条”“财政部令第87号”和完整法规名属于确定性信号，纯向量检索可能把相近数字或其他法规的同号法条排在前面。

**修改措施**

- 解析中文数字和阿拉伯数字条号并归一化。
- 提取法规标题、文号和准确短语。
- 只有法规名和条号在同一候选中同时满足时，才认为正式引用命中。
- 将精确匹配原因写入 `exact_matches` 和 retrieval trace。

**结果**

准确编号问题可以通过确定性信号优先召回，不再完全依赖向量距离。该逻辑与混合检索同时评测，没有独立消融值。

## 优化 10：加入 BM25 词法检索

**原本是什么**

只有向量召回。

**存在的问题**

向量擅长语义相似，但对法规名、文号、条号、金额、期限和少见专有名词不一定稳定。

**修改措施**

- 为全部 child 预计算词频、文档频率、文档长度和平均长度。
- 使用 `k1=1.2`、`b=0.75` 的 BM25 评分。
- 将精确编号分叠加到词法分，并按 collection 名称和数量缓存词法索引。

**结果**

词法通道与向量通道互补，构成父子混合检索的一部分。10题 v1 组合优化后 Recall@5达到0.80；没有仅开关 BM25 的单独结果。

## 优化 11：RRF 多通道融合

**原本是什么**

不同召回通道的分数尺度不同，BM25 分、精确匹配分和向量距离不能直接相加。

**存在的问题**

手工给不同原始分数设置权重容易受语料和模型变化影响。

**修改措施**

- 每一路先独立排序。
- 使用 Reciprocal Rank Fusion：`score += 1 / (RRF_K + rank)`。
- `RRF_K` 默认60，并记录候选来自哪些通道。

**结果**

实现无量纲排名融合，支持后续继续增加问题式、答案式和关键词式通道。该项与混合检索整体评测，没有独立消融值。

## 优化 12：扩大每路候选池

**原本是什么**

每路只取较少候选，正确法条可能在融合前被截断。

**存在的问题**

Recall 较低时，Reranker 看不到正确候选，后续排序再强也无法找回。

**修改措施**

- 每路候选数设置为 `max(top_k × 8, 20)`，Top-K=5时取40个。
- 在10题对照中，20个候选命中7题，40/60/80个均命中8题，因此选择40个控制成本。

**结果**

40个候选达到该对照中的最高命中数，同时比60或80个候选更节省融合与内存成本。这是小规模开发集调参结果，需要在更大评测集继续验证。

## 优化 13：将字符哈希替换为中文语义 Embedding

**原本是什么**

128维字符哈希通过字符出现次数生成向量，完全离线且速度快，但不理解语义。

**存在的问题**

同义表达、自然语言场景题和法规原文的语言形式不一致时，字面重合不足。

**修改措施**

- 加入 BGE-small-zh-v1.5 512维中文 Embedding。
- 区分 document 和 query 编码接口，批量生成文档向量。
- collection 名携带模型和维度后缀，防止128维旧向量与512维新向量混库。
- 保留 hash backend，用于无模型测试和消融实验。

**结果**

同一50题、无 Reranker 条件下：Recall@1从0.45升至0.57，Recall@3从0.70升至0.84，Recall@5从0.84升至0.90，MRR@5从0.6107升至0.7140。平均延迟从158.85 ms升至361.80 ms。

## 优化 14：加入 BGE Reranker

**原本是什么**

RRF 只能融合名次，无法像交叉编码器一样联合理解“问题和候选法条”。

**存在的问题**

正确法条已经召回，但可能排在第2至第5位；最终回答收到过多干扰上下文。

**修改措施**

- 使用 bge-reranker-base 的量化 ONNX 模型。
- 对融合后的前20个 child 做交叉编码打分。
- Reranker 失败时保留融合结果并返回 warning，不让在线服务完全中断。
- 按 parent ID 合并 child，再回填完整 parent。

**结果**

同一50题 BGE 配置下：Recall@1从0.57升至0.62，Recall@5从0.90升至0.95，MRR@5从0.7140升至0.7530；平均延迟从361.80 ms增加到5969.48 ms。

**代价与下一步**

Reranker 是当前最大延迟来源。下一步应测试更小模型、INT8优化、动态批处理、减少候选、结果缓存或 GPU 推理，并同时观察 Recall 和 P95，不能只优化速度。

## 优化 15：父块回填和多来源输出

**原本是什么**

直接返回命中的固定字符 chunk，一次命中只能看到局部文本。

**存在的问题**

法律条文的但书、例外、条件和法律后果可能位于同一法条后半部分，只返回 child 容易断章取义。

**修改措施**

- child 排序后按 parent ID 去重。
- 从 parent collection 批量获取完整法条或章节。
- API 同时返回 `quote`、`matched_child_quote`、`matched_child_chunk_id`、`parent_id` 和多个来源标题。

**结果**

系统实现“精细检索、完整回答”，并支持一个问题返回多部法规证据。该项主要改善上下文完整性和解释性，没有单独生成质量评测。

## 优化 16：问题式、答案式和关键词式二次召回

**原本是什么**

一次原问题检索失败后直接返回低质量结果或空结果。

**存在的问题**

用户口语表达、事实描述和法规原文差异较大时，一种查询表达可能无法覆盖正确法条。

**修改措施**

- 问题式：保持原意重新组织为法律问题，同时进入 BM25 和向量检索。
- 答案式：生成不包含虚构法规名、条号、金额的中性假设答案，只进入向量检索。
- 关键词式：提取法规名、主体、行为、条件、数字和专有名词，进入 BM25。
- 配置 LLM 时一次生成三种表达；未配置时使用确定性模板，并把来源写入 trace。
- 只在初次证据门认为需要重试时执行，避免每个问题都承担多路召回成本。

**结果**

已实现多路补召回并用于无答案拒答流程。最终50道有答案题的二次召回触发率为0%，因此没有证据证明该机制提升了这50题的 Recall；最终版本平均延迟8429.10 ms，也说明安全判断和多阶段处理仍需做性能优化。

## 优化 17：证据充分性判断

**原本是什么**

只要 Chroma 返回 Top-K，就把结果交给回答器。

**存在的问题**

向量数据库几乎总能返回“最相似”的结果，但最相似不等于足以支持法律结论。

**修改措施**

- 检查 Top 候选 Reranker 分数。
- 计算问题关键词在候选证据中的加权覆盖率。
- 检查有多少检索通道支持同一候选。
- 问题含法规名、条号或文号时，要求正式引用信号在同一候选中满足。
- 把初次判断、最终判断、阈值和失败原因写入 `retrieval_trace`。

**结果**

50道有答案题全部放行，错误拒答0；10道无答案题全部被拒答。阈值仍是当前模型和开发集上的工程参数，不是经过概率校准的法律可信度。

## 优化 18：在最终模型调用前拒答

**原本是什么**

即使证据相关性低，也可能让生成模型根据候选自由组织答案。

**存在的问题**

法律领域中，语言流畅但证据错误的回答比明确说“不足”风险更高。

**修改措施**

- 证据门失败时不调用最终回答模型。
- 不把失败候选放进正式 citations。
- 返回 `insufficient_evidence=true`、`refusal_reason` 和补充法规名/条号/事实的提示。

**结果**

10道无答案开发集正确拒答10/10、不安全回答0；有答案集错误拒答0/50。

**证据边界**

10题规模较小，不能写成生产环境“100%拒答准确率”。

## 优化 19：证据约束的回答和离线降级

**原本是什么**

回答功能依赖可选大模型。

**存在的问题**

API Key 缺失、模型服务故障或网络中断时，整个知识库可能不可用；模型也可能新增未提供的法条或日期。

**修改措施**

- 未配置 LLM 时返回透明的原文证据式回答。
- LLM 提示词要求只能依据给定证据，不得新增条号、日期或结论。
- 模型调用失败时回退到本地检索回答，并返回不包含密钥的 warning。
- 证据不足拒答发生在模型调用之前。

**结果**

系统不依赖外部 LLM 也能完成检索、引用和拒答；启用模型后只负责组织已放行证据。最终版本已启动完整 RAGAS 评测，但因评测账户余额不足仅有42/50题完成五项指标，仍不能作为完整最终结论。

## 优化 20：从10题扩展到50题评测集

**原本是什么**

只有10道单法条人工 gold，题型和法规覆盖不足。

**存在的问题**

少量简单题很容易受到偶然命中影响，也无法分别评估自然语言、数值、场景和多证据问题。

**修改措施**

- 扩展到50道有答案题、52条 gold evidence、50个唯一 gold parent。
- 覆盖 definition、exact_article、law_application、legal_consequence、multi_evidence、numeric_fact、paraphrase、procedure、scenario、single_article_list。
- 增加 gold 数据审计，检查文档、parent、条号和引用是否真实存在。

**结果**

形成可用于 Embedding 与 Reranker 消融的统一50题开发集；gold 审计通过。该数据集仍不是独立测试集，后续需要冻结开发集并增加不参与调参的测试集。

## 优化 21：增加 RAGAS 与确定性检索指标

**原本是什么**

只通过手工查询观察结果。

**存在的问题**

无法量化 Top-K 是否命中、正确结果排第几，也无法复现实验。

**修改措施**

- 确定性计算 parent Recall@1/3/5、MRR@5、文档命中率、法条命中率和 ID Context Precision/Recall。
- 记录平均、P50、P95和冷启动延迟。
- 可选使用 RAGAS LLM Context Precision/Recall，但与确定性 gold 指标分开报告。

**结果**

首次10题字符哈希基线的 RAGAS LLM Context Precision=0.3567、Context Recall=0.5000；最终主要优化使用50题确定性指标进行比较，避免把 LLM 裁判分数当成唯一结论。

## 优化 22：建立无答案拒答评测集

**原本是什么**

评测只关心“有答案时能否召回”，没有测试“知识库没有答案时会不会乱答”。

**存在的问题**

高 Recall 系统可能对不存在的法条、域外法规和案件预测问题仍然输出确定答案。

**修改措施**

- 建立10题无答案集。
- 覆盖不存在条号、美国/欧盟规则、缺失地方政策、错误数值前提、知识库外事实、案件结果和缺少时效元数据。
- 分别统计正确拒答和不安全回答。

**结果**

当前开发集正确拒答10/10、不安全回答0。由于没有使用 LLM 裁判且题量较小，只能作为当前规则的回归测试。

## 优化 23：参数化与可复现实验

**原本是什么**

切块和检索参数部分写死在代码中，模型文件可能自动变化。

**存在的问题**

难以进行消融，也容易把不同维度向量或不同模型结果混在一起。

**修改措施**

- 将切块、Embedding、Reranker、候选数、RRF和证据门阈值集中到 `shared/config.py`，支持 `.env` 覆盖。
- 下载脚本固定 Hugging Face revision，并校验 Reranker ONNX SHA-256。
- collection 名包含版本、模型和向量维度。
- retrieval trace 返回实际 backend、候选数、阈值和通道。

**结果**

可以通过环境变量重复运行 hash/BGE、开启/关闭 Reranker、改变证据门阈值等对照实验。该项改善复现性，没有独立质量指标。

## 优化 24：API 响应可解释性

**原本是什么**

只需要返回问题、回答和简单来源。

**存在的问题**

前端和调试人员无法知道为什么召回、是否触发重试、使用了哪个 child 或为什么拒答。

**修改措施**

- `/health` 返回 child 和 parent 数量。
- `/api/v1/questions` 返回多来源 citations、source_titles、generation_mode、warning、insufficient_evidence 和 refusal_reason。
- citation 中同时包含 parent 全文、matched child、条号、章节、页码、来源 URL、精确匹配原因、RRF分和Reranker分。
- retrieval trace 返回查询变体、通道、阈值、两轮证据评估和候选数量。

**结果**

API 可以支持前端证据展示、线上问题复盘和面试演示。该项属于可观测性优化，没有独立 Recall 指标。

## 优化 25：项目自包含迁移和 Windows 中文路径兼容

**原本是什么**

RAG 代码、法律汇集和索引分别位于多个磁盘目录，配置依赖旧绝对路径；复制 Chroma 大索引到包含中文的绝对路径后，Windows 下跨进程重开 HNSW 段失败。

**存在的问题**

项目无法作为独立面试工程交付，数据库虽然复制成功但重启后不能查询。

**修改措施**

- 将代码迁移到 JurisRAG，将原文统一放入 `data/source`，派生 Markdown 放入 `data/processed`，Chroma 放入 `data/index`。
- 所有默认路径改成项目根目录相对路径，并允许 `.env` 覆盖。
- 只迁移当前 BGE child/parent collection，通过 Chroma API 重写索引，而不是保留历史实验集合。
- Windows 中文目录下，传给 Chroma 的持久化地址改为项目内 ASCII 相对路径；数据库物理位置不变。
- 不复制虚拟环境、模型缓存、IDE 文件、临时文件和大型历史评测输出。

**结果**

目标目录可跨进程重开 Chroma，`/health` 返回2,299个 child和1,565个 parent；实际问题“政府采购法第二十二条规定了哪些供应商条件”成功命中第二十二条。加入当前 Agent 和可靠性代码后完整测试38项通过，`pip check`通过。

## 优化 26：MCP 工具化与受约束 LangGraph Agent

**原本是什么**

在线检索由固定 Python 调用链控制。即使规划模型认为证据不足，也只能执行预先写好的一次问题式、HyDE 和关键词式补召回；没有跨轮状态、工具白名单、重复动作拦截和统一停止原因。

**存在的问题**

- 精确法条、关键词、语义、HyDE、父块和覆盖检查都埋在同一检索函数里，外层 Agent 不能按证据缺口选择能力。
- 模型输出错误工具名、错误参数或重复查询时，没有独立策略层拦截。
- 回答审查失败容易被误写成“完全没有证据”，没有区分模型归纳失败与检索证据不足。
- 固定 RAG 与 Agent 无法在同一页面和 API 中对照。

**修改措施**

- 使用官方 MCP Python SDK，把精确、BM25、语义、HyDE、多查询、parent、适用范围、溯源和争点覆盖封装为九个结构化只读工具；声明只读、幂等、非破坏和非开放世界属性。
- 使用 LangGraph 实现输入验证、意图/领域/术语/争点、动作选择、MCP 执行、观察、覆盖、parent、回答、验证、纠正、拒答和固定 RAG 降级节点。
- 使用 Pydantic 校验模型和工具参数；以“工具名 + 规范 JSON 参数”的 SHA-256 签名拦截完全重复动作。
- 对模型生成的争点列表执行去空、去重、保序和上限截断。模型偶发返回超过 Schema 上限的辅助争点时，保留前六项继续运行，而不是让整条 API 因非关键数组过长返回 502；法规证据正文不参与该截断。
- 限制最多3轮检索、8次 MCP 调用、7次可计数模型调用、2次纠正、连续2次无新增证据和90秒图预算。
- 回答执行法规名、条号、数字、citation ID 和 LLM 蕴含检查；模型归纳连续不通过时撤销其结论，保留带引用的原文证据，而不是错误清空证据。
- 新增 `/api/v1/agent/questions`、Agent 健康检查、Web 模式切换、公开 Agent trace 和10题工程冒烟评测入口；原固定 RAG 接口不删除。

**当前实际结果与边界**

- 当前完整测试为38项通过，`pip check`通过，`compileall`通过；两个警告来自 Chroma 与 Pydantic Settings 的第三方弃用/前向引用提示，不影响当前测试结果。
- Streamable HTTP MCP 实测发现9/9个工具，模型、MCP、Embedding 和 Reranker 健康状态均就绪。
- 精确问题《政府采购法》第二十二条实测一轮完成：3次 MCP 调用、4次可计数模型调用、55.87秒，返回 `direct` 和一个可回溯 parent 引用。
- “超过150页能否否决”先后暴露并修复了两类边界：一是覆盖已充分但回答审查失败后错误清空引用，二是规划模型返回9个 `target_issues` 超过 Schema 上限导致接口失败。后者增加列表归一化测试后，2026-08-26 同题在线回归在81.24秒内成功完成2轮，使用 `agent_llm` 返回条件式结论和2个可回溯 parent 引用；回答明确区分“页数条件能否设置”和“违反后能否直接否决”，未把一般公平性条文误写成当然否决依据。
- 尚未运行固定 RAG 与 Agent RAG 的完整冻结 A/B，不能声称 Agent 已经提高 Recall、Faithfulness 或法律正确率。10题 Agent 冒烟集目前只是评测入口，不是已完成结果。

## 优化 27：分层约束、出站验证与单进程高可用保护

**原本是什么**

Agent 已有轮数、工具数、模型数和纠正数预算，也能在 MCP 不可连接时降级到固定 RAG，但 HTTP、模型、MCP、固定 RAG 降级和最终响应之间缺少统一的运行时保护。

**存在的问题**

- 单次模型调用只能依赖整图超时，某个供应商请求挂起会吃掉后续降级机会；
- MCP 每次请求创建新客户端，连续故障无法跨请求熔断；服务宕机时每个用户都可能等待完整连接超时；
- `structuredContent` 是 JSON 对象不等于字段正确，`count/results` 不一致或证据缺少 ID/正文仍可能进入状态；
- 没有进程内并发舱壁，CPU Reranker 和外部模型可能因请求堆积雪崩；
- `/health` 没有区分进程存活、核心索引就绪和 Agent 依赖降级；
- 最终状态可能出现“可回答但没有引用”或“证据不足却携带引用”的矛盾，缺少出站失败关闭；
- API请求与Agent trace没有共用一个可由响应头定位的请求ID。

**修改措施**

- 增加问题2,000字、单次LLM 35秒、MCP会话30秒、Agent图90秒、固定RAG降级25秒和端到端120秒的分层预算；任一依赖超时都只能确定性降级或安全拒答。
- API进程复用同一个 MCP Client 熔断状态：连接最多尝试2次，连续3次连接失败后熔断30秒，冷却后半开探测；工具执行错误、参数错误和响应Schema错误不触发网络重试。
- 对九个工具的 `structuredContent` 校验工具名；对结果型工具校验对象数组、`count`一致、最多20项；正式证据必须具有稳定ID和非空正文；覆盖检查校验可回答性枚举、继续标记和证据编号映射。
- 增加进程内并发舱壁，默认最多同时执行2个Agent请求；容量用尽时返回HTTP 503和`Retry-After: 2`，请求结束后在`finally`路径释放槽位。
- 新增 `/live`、`/health`、`/ready` 和增强的 Agent health。MCP故障但固定RAG可用时返回`degraded`而非假报整个服务宕机；核心索引不可用时`/ready`返回503。
- 为HTTP响应增加经过字符白名单清洗的 `X-Request-ID` 和 `X-Process-Time-Ms`；正文、密钥、Authorization和隐藏思维链不进入访问日志。
- 出站前执行最终契约：直接/条件式回答必须有不重复的法规名、证据ID和原文引用；证据不足必须无引用；矛盾状态转成 `agent_operational_abstention`，不带错误结论继续返回。

**结果与边界**

- 新增11项故障路径测试，完整自动化测试从27项增加到38项，全部通过；覆盖超长/纯空白输入、非法请求ID、就绪降级/未就绪503、MCP数量不一致、不可追溯证据、熔断、并发释放/并发满503、模型超时和无引用结论。
- 这些测试证明的是确定性工程行为，不是吞吐量或可用性百分比；尚未执行并发压测，因此不能写“支持多少QPS”或“达到99.9%可用性”。
- 当前熔断和并发计数只在单个API进程内有效。真正多副本部署仍需要网关限流、进程守护、集中指标/告警和跨实例策略；项目没有虚构Redis、Kubernetes或自动容灾。

## 五、哪些优化已经证明，哪些仍需继续验证

### 已有同集对照支持

- 父子切块加混合检索：10题 v1 Recall@5 从0.50到0.80。
- 中文 Embedding：50题 v2 无 Reranker 时 Recall@5 从0.84到0.90。
- Reranker：50题 v2 使用 BGE 时 Recall@5 从0.90到0.95，MRR@5从0.7140到0.7530。

### 已实现但缺少独立消融

- 结构化 Markdown、页码、元数据对最终回答正确性的单独贡献。
- 精确匹配、BM25、RRF、候选扩展和 parent 回填各自独立的质量贡献。
- 多路召回和 HyDE 对困难有答案题的提升，因为当前50题没有触发重试。
- LLM 最终回答的完整50题 Faithfulness、Factual Correctness 和引用覆盖率；当前仅42题完成全部五项评分。
- 受约束 Agent 已完成真实协议和单题闭环，但尚未完成冻结困难集 A/B，因此不能归因质量提升。

### 下一阶段优先级

1. **P0：运行并扩充 Agent 冻结 A/B。** 当前只有10题工程冒烟入口；应人工审核争点、适用领域、可接受工具和答案边界，再与固定 RAG 同集对照。
